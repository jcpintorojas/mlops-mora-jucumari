MLOps de mora en Jucumari

Un modelo sobre créditos reales del ERP: Python entrena, MLflow versiona y una API en Node.js lo sirve en Kubernetes, con detección de drift.

Apliqué el proyecto a mi ERP, Jucumari. La pregunta es de negocio: al vender a crédito, ¿este crédito se va a atrasar? El foco no es la exactitud, sino la ingeniería: trazabilidad, servicio reproducible, alta disponibilidad y monitoreo. Y el monitoreo terminó siendo lo más valioso.
El problema

¿Este crédito se atrasará más de 30 días?

1.620
créditos, 1.519 con resultado conocido
14

33,4 %

Qué usa el modelo

  • Monto, plazo y cuota inicial
  • Créditos anteriores y cuántos se atrasaron
  • Mayor atraso y saldo que aún debe
  • Solo lo que se sabía el día de la venta

Cómo se evalúa

División por fecha: entreno hasta junio de 2024 (687) y pruebo hasta septiembre de 2025 (446), porque en la vida real se predice el futuro. Lo posterior queda para el monitoreo (lámina 12).

Métrica: ROC AUC. Referencia a superar: la regla del negocio, "si su crédito anterior se atrasó, este también".

Uso datos reales de mi ERP, sin nombres, CI ni teléfonos. La unidad es un crédito al momento de otorgarlo. Solo uso lo conocido ese día, para evitar fuga de información. Divido por fecha, y comparo contra una regla simple, porque un modelo solo vale si le gana.

A la izquierda, Python: saca los datos y entrena. MLflow guarda experimentos, versiones y artefactos. En el clúster hay 3 réplicas de Node detrás de un Service. Los Pods no llevan el modelo en la imagen: preguntan qué versión tiene champion y bajan sus coeficientes. El monitoreo corre aparte.

Etapa 4 · API en Node.js y Docker

Se entrena en Python y se sirve en Node

Decisiones

  • El ERP ya es Node: no sumo otro lenguaje en producción
  • Node no carga scikit-learn: exporto los coeficientes como artefacto del mismo run
  • La API pide mora-credito@champion por REST; MLflow resuelve versión y run, y rechaza un artefacto de otro run
  • MLflow se fija al entrenar (3.14.0) y la API exige esa versión del servidor
  • Costo: solo sirve logísticas; con el bosque, los Pods nuevos no quedan listos

300 casos inventados, iguales a scikit-learn a 4 decimales. Arranca sin pasos manuales: docker run → /ready → /predict.

Entrenar y servir son trabajos distintos. Node no puede cargar scikit-learn, pero la regresión logística es una suma, y la calcula con sus coeficientes. Esos números son un artefacto del mismo run: la API pide por alias y rechaza un artefacto de otro run, así que la trazabilidad no se pierde. Comprobé con 300 casos inventados que da lo mismo que scikit-learn, a 4 decimales. La API no instala MLflow: lo consume por REST y exige la versión fijada. El límite es que solo puedo servir logísticas.

Etapa 6 · Data drift

La prueba pasa en verde y falla en rojo cuando debe

Qué aplico y por qué

  • Numéricas: KS. No supone normalidad y los montos son asimétricos. Alerta si p < 0,05/11 = 0,0045 (Bonferroni)
  • Categóricas: PSI. Alerta 0,10; drift 0,20, convención de la industria
  • Lotes reales: rojo en 12 de 14 variables. El historial del cliente crece con el tiempo: es esperable, no una falsa alarma. Incluyen créditos sin resultado, por eso tienen más filas que la lámina 12

Etapa 6 · Concept drift simulado

La alarma salta cuando el rendimiento cae de forma sostenida

Criterio

  • Desde el lote 5, quien tenía buen historial pasa a atrasarse y al revés (simula un cambio de cobranza)
  • Umbral: referencia − 2σ = 0,498; σ = 0,070, medida en 200 muestras de 60
  • 3 lotes seguidos bajo el umbral
  • Alarma en el lote 10

Son muestras de 446 créditos, no lotes independientes.

Simulo un cambio de cobranza: la relación entrada-salida se invierte. El umbral sale de la variación normal del AUC. Pido tres lotes seguidos para no reaccionar a un lote raro. Hice dos ajustes tras ver el resultado: la regla inicial subía el AUC y con 7 lotes no se cumplía el criterio. El criterio no cambió.

La venta real de Jucumari consulta la API en Kubernetes

Cómo funciona

  • El vendedor elige al cliente y carga productos y plazo
  • El backend de Node calcula su historial con SQL
  • Lo envía a la API, y Jucumari muestra riesgo, motivos, versión, run y Pod

Esta es la prueba más real: la pantalla de venta del ERP, en local. El vendedor no escribe el historial: elige al cliente y el backend lo calcula con SQL, con la misma definición del entrenamiento. Si el cliente no tiene créditos vencidos, no muestra porcentaje: una prueba me dio 69,9 % a un cliente sin créditos, porque el modelo extrapolaba. Comprobé que si apago la API la venta sigue igual. Los clientes son inventados, y el modelo no está en producción.
Prueba en el ERP · El recorrido

De la pantalla a la decisión: quién hace qué

Antes de vender: Python aprende los pesos, MLflow los versiona y cada Pod los carga por alias al arrancar. Durante la venta no aprende nada.

Sigamos un crédito. En la pantalla eliges cliente, productos y plazo. La guardia comprueba la sesión y el privilegio. El backend calcula con SQL el historial del cliente; si no tiene créditos vencidos, no llama a la API. Si tiene, envía 14 datos a Kubernetes, y el Service elige un Pod. La API suma los pesos y da el porcentaje. La API no recibe nombre ni CI. El backend traduce los motivos, y la tarjeta aparece en la pantalla. Quien decide es el vendedor: el sistema nunca bloquea la venta, y si algo falla se vende igual.
Cierre

La ingeniería funciona, y por eso sabemos que el modelo sigue en beta

Lo que logramos

  • Trazabilidad de la predicción al run y a los datos
  • API en Node en 3 réplicas, con autorreparación
  • Drift detectado: simulado y real
  • Una decisión con evidencia: no promover

Límites y siguiente paso

  • Una empresa y pocas variables; la fecha de pago se puede corregir a mano, y puede contaminar la etiqueta
  • Madurez 0-1: trazable, pero a mano; falta automatizar el reentrenamiento
  • Preguntar al negocio qué cambió desde 2025
  • Empezar por la ficha del cliente

El criterio evitó poner en uso un modelo que aún no está validado. Esa es la razón de hacer MLOps.

Cierro con esto: la ingeniería funciona de punta a punta, y justamente por eso detectamos que su rendimiento cayó y decidimos no llevarlo a las ventas hasta entender qué cambió. Gracias.
